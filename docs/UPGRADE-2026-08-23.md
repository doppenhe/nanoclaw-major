# Upgrade runbook — upstream 2026-08-23 (255 commits, 5 breaking changes)

The weekly job stopped at the build gate on 2026-08-23 and hard-reset. This
runbook takes the same upgrade the rest of the way. The code half is already
done and pushed on branch `claude/eager-johnson-waxxnr` — most of what follows
is verifying it on your host and rebuilding the container.

**Status of the branch**: merge resolved, `pnpm run build` clean,
`pnpm test` 2048/2049, container typecheck clean,
`bun scripts/detect-driver-migration.ts` clean. Every fork customization is
intact, GitHub push auth included. What is NOT verified: anything needing
Docker or your live database — the sandbox has neither. Those are steps 4–8.

---

## Why the job failed, in one paragraph

Upstream shipped 255 commits in the week of Aug 16–23, including the two
largest refactors in the project's history: the session-driver seam (Aug 18)
and async central-database access (Aug 19, 243 files). The async change made
every DB call return a Promise. Our Telegram adapter is skill-installed and
pinned, so it was still calling them synchronously and failed to compile. The
scheduled job has no `/update-skills` step, so it could not fix that itself.
Separately, the driver seam added an admission rule that refuses credentials in
container environment variables — which is exactly how our GitHub push auth
worked. Both are addressed on the branch.

## Step 4 — Check your group folders (2 min)

The new runtime label grammar refuses group folder names longer than 63
characters, containing anything outside `[A-Za-z0-9_-]`, or not
alphanumeric at both ends. A group whose folder breaks the rule **refuses to
spawn** — it does not degrade.

```bash
bun scripts/detect-driver-migration.ts
```

This must be run **on your host**. It came back clean in the sandbox, but the
sandbox is a fresh clone with no `groups/` directory, so that result means
nothing. Your install has real folders and is the only place the answer is
real.

If it flags a folder, the fix is three steps and the host must be stopped for
it:

```bash
systemctl --user stop nanoclaw-v2-6c8430b5.service
mv "groups/<old-name>" "groups/<new-name>"
pnpm exec tsx scripts/q.ts data/v2.db \
  "UPDATE agent_groups SET folder='<new-name>' WHERE folder='<old-name>'"
```

If it fails, diagnose in this order:

```bash
# 1. Did the host compose a token mount at all?
grep "GitHub token mount composed" logs/nanoclaw.log | tail -3

# 2. Does the token file exist while a session is live?

# 3. Can the host resolve a token at all?
```

that `groups/global` is a git checkout with a `doppenhe/` remote. If #3 fails,
`gh auth login --hostname github.com --user doppenhe`.

## What changed in the fork, and why

### GitHub push auth — reworked, same behavior

**Before**: the host ran `gh auth token`, passed it as a value-less
`-e GH_TOKEN`, and the image's git credential helper read `$GH_TOKEN`.

**Why that stopped working**: `validateSpec` in `src/drivers/types.ts` now
refuses a `_TOKEN`-suffixed key on the `env` lane and a `gho_`/`ghp_`-shaped
value on both env lanes. Admission is fail-closed, so the old shape would abort
every spawn that mounts a doppenhe checkout — not degrade, abort.

**Now**: the token is written to `data/gh-tokens/<session>.token` at 0600,
mounted read-only at `/run/nanoclaw/gh-token`, and the container reads
`$GH_TOKEN_FILE`. `isSecretShaped` exempts absolute-path values by design —
this is the by-reference pattern upstream documents. The file is deleted when
the session ends.

All of it lives in a new file, `src/fork-github-auth.ts`, rather than inline in
`container-runner.ts`. That file is upstream's session-composition hot path and
now gets rewritten often; keeping our logic out of it means next week's merge
touches three call sites instead of seven conflict hunks.

**Be clear-eyed about what this is**: it restores the previous capability and
the previous exposure. An agent that can read `/run/nanoclaw/gh-token` holds a
GitHub token, just as it did when the token sat in its environment. What
changed is that admission can now see the mount and reason about it. OneCLI is
not an alternative here — its gateway special-cases github.com and returns 401
for raw PATs, which is why the `NO_PROXY` bypass exists.

`src/fork-github-auth.test.ts` pins both directions: the new shape passes
admission, the old shape is still refused. Do not "simplify" it back to an env
var — the suite will catch you, which is the point.

### Telegram adapter — refreshed from the `channels` branch

Refreshed `telegram.ts`, `telegram-pairing.ts`, and the pairing test. The new
version awaits the DB calls and adds upstream's multi-instance support
(`instanceKey`).

**Deleted**: `telegram-markdown-sanitize.ts` and its test. Upstream removed the
`transformOutboundText` hook deliberately —
`@chat-adapter/telegram` >= 4.29 parses CommonMark and renders escaped
MarkdownV2 itself, and running the legacy sanitizer in front of it downgraded
`**bold**` to `*single-star*`, which the adapter then rendered as *italic*.
We are already pinned at 4.29.0, so removing it is a fix. Nothing else imported
it.

### `groups/global` mount — same behavior, new mount class

Still read-only by default, read-write when it is a git checkout. Now carries
`mountClass: 'allowlisted-extra'`. It cannot be `group-state`: admission pins
that class to the session's own `groups/<folder>` subtree, and `global` sits
outside any single folder.

### Everything else — verified intact

`WEBHOOK_PORT` from `.env`, the `@chat-adapter/telegram` 4.29.0 pin, shmem in
the Dockerfile, and all nine container skills (`status`, `capabilities`,
`wiki`, `pdf-reader`, and the upstream five).

Upstream moved `src/db/session-db.ts` to `src/mailbox/sqlite/session-db.ts` and
`src/modules/scheduling/db.ts` to `src/mailbox/sqlite/tasks.ts`. The merge
applied both moves cleanly and left no orphans.

The database restore matters: migrations ran forward on first start and there
is no reverse path. Rolling back code without restoring the DB leaves old code
against a new schema.

## Fix the weekly job before the next run

The job is missing a skill-refresh step, which is what made this an outage
instead of an ordinary week. Between the merge (Step 6) and the build (Step 8)
of the scheduled prompt, it needs to re-apply installed channels and providers
from their registry branches — `/update-skills` when a session has the Skill
tool, or the equivalent `git checkout upstream/channels -- <paths>` when it
does not.

Also worth changing: the job currently pushes straight to `main` on success.
Pushing to a branch and opening a draft PR costs nothing on a clean week and
gives you a review surface on a week like this one.
